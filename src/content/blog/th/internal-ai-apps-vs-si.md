เมื่อองค์กรไทยขนาดใหญ่ตัดสินใจว่า "ต้องทำอะไรสักอย่างกับ AI" บทสนทนามักไหลไปหาเครื่องมือที่ใหญ่ที่สุดที่มี: โปรเจกต์ systems integration (SI) หลายปีที่แตะ core system บางครั้งนั่นถูกต้อง แต่บ่อยครั้งมันคือคำตอบของคำถามผิด สองสิ่งนี้คือเครื่องมือคนละแบบ และการเลือกผิดแพงทั้งสองทาง

## แต่ละแบบคืออะไรกันแน่

**โปรเจกต์ SI แก้ core system** คือการเปลี่ยนหรือปรับระบบหลักอย่างลึก: ledger, ระบบบริหารกรมธรรม์, core banking, ERP เป็นคำมั่นหลายปีที่มาพร้อมคณะกรรมการ phase gates, data migration และ regression testing เมื่อ core system ของคุณจริง ๆ ไม่รองรับธุรกิจ — เทคโนโลยีเก่า ผู้ขายเลิกซัพพอร์ต แรงกดดันด้านกฎระเบียบ — นี่คือเครื่องมือที่ถูกต้อง และ AI มักไม่ใช่เหตุผลที่ควรเริ่มมัน

**Internal AI app** คือเครื่องมือแบบมีขอบเขตที่สร้าง *เคียง* core system ไม่ใช่ข้างใน มันอ่านข้อมูลที่ core system ผลิตอยู่แล้ว ทำงานทางความคิดอย่างใดอย่างหนึ่ง — ร่าง สรุป ตรวจ กระทบยอด จัดเส้นทาง — แล้วส่งผลลัพธ์กลับให้คนหรือระบบหลักผ่าน interface มันมีอายุเป็นสัปดาห์ ไม่ใช่ปี

| มิติ | โปรเจกต์ SI แก้ core system | Internal AI app แบบมีขอบเขต |
|---|---|---|
| เวลาถึงคุณค่าแรก | 12–36 เดือน | 4–8 สัปดาห์ (pilot) |
| ความเสี่ยงหลัก | migration, ขอบเขตบาน, regression | แคบมาก: งานเดียวไม่ผ่าน |
| รูปทรงงบ | ก้อนใหญ่ หลายปี หนักช่วงต้น | เล็ก ต่อ pilot หยุดได้ |
| ความเสี่ยงข้อมูล | ทุกอย่างต้องย้าย | ไม่ต้องย้ายอะไรเลย |
| เจ้าของงาน | IT + vendor + เจ้าของกระบวนการ | ทีมธุรกิจหนึ่งทีม + ผู้สร้าง |
| ตัวชี้วัดความสำเร็จ | milestone ของโปรเจกต์ | ตัวชี้วัดเชิงปฏิบัติการหนึ่งตัว |

## กับดัก: เลือกด้วยความทะเยอทะยาน แทนที่จะเลือกด้วยปัญหา

โปรเจกต์ SI กับ internal AI app ไม่ใช่คู่แข่งบนเวทีเดียวกัน — มันแก้คนละปัญหา กับดักคือการจับคู่ขนาดของคำตอบกับขนาดของความวิตกกังวล ("เราต้อง transform") แทนที่จะเป็นขนาดของปัญหา ("ทีมการเงินเสียเวลา 60 ชั่วโมงต่อเดือนกับงานทวงหนี้")

ความวิตกอยากได้โปรแกรมใหญ่ ปัญหาอยากได้เครื่องมือ

## สามสัญญาณว่าควรเริ่มจาก internal app แบบมีขอบเขต

**1. ความเจ็บปวดอยู่ที่งานความคิด ไม่ใช่โครงสร้าง** ถ้าระบบผลิตข้อมูลที่ถูกต้องแล้ว แต่คนใช้เวลาไปกับการอ่าน ร่าง เทียบ และตรวจ — นั่นคือเขตของ AI app การเปลี่ยนระบบที่ผลิตข้อมูลไม่ทำให้งานอ่านหายไป

**2. กระบวนการข้ามหลายระบบแต่ไม่เป็นของระบบไหน** งาน operations จำนวนมาก — การทวงหนี้ การกระทบยอดลูกค้า การจัดคิวงานบริการ — ทอดข้าม ERP, CRM และไฟล์ Excel โดยไม่อยู่ในระบบใดระบบหนึ่ง การเปลี่ยน core system ไม่มีทางแก้งานข้ามระบบ เพราะไม่มี core system เดียวที่บรรจุมันทั้งหมด

**3. คุณต้องการหลักฐานภายในปีนี้** คณะกรรมการไม่ยอมรับ "transformation จะเห็นผลปีที่สาม" อีกต่อไป แอปที่มีขอบเขตให้ตัวเลขภายในไตรมาส — และตัวเลขนั้นคือทุนทางการเมืองจริงสำหรับการตัดสินใจถัดไป

## สองสัญญาณว่าคุณจำเป็นต้องมีโปรเจกต์ SI จริง ๆ

**1. core system คือคอขวด** ถ้า ledger เดินทางไม่พอสำหรับสินค้าที่คุณขายทุกวันนี้ หรือแพลตฟอร์มหมดการซัพพอร์ตและแพตช์ไม่ได้ AI เท่าไรก็ช่วยไม่ได้ นั่นคือปัญหาการเปลี่ยนระบบ

**2. โครงสร้างข้อมูลรากผิดตั้งแต่ต้น** เครื่องมือ AI ต้องการข้อมูลนำเข้าที่มีโครงร่างพอควร ถ้าข้อมูลหลักของคุณขัดแย้งกันเองจนซ่อมไม่ไหว — ข้อมูลลูกค้าซ้ำซ้อน รหัสสินค้ากระทบยอดไม่ได้ — การวางรากให้แน่นอาจต้องมาก่อน

## ทั้งสองแบบต่อกันอย่างไรในทางปฏิบัติ

ข่าวดีคือนี่ไม่ใช่ทางแยกที่ต้องเลือกข้างเดียว ลำดับที่ใช้ได้ผลกับองค์กรไทยส่วนใหญ่คือ:

1. รัน internal AI pilot แบบมีขอบเขตหนึ่งถึงสองงานที่เจ็บจริง
2. ปล่อยให้งาน integration ที่ pilot ต้องใช้บอกคุณว่า core system ขวางจริงตรงไหน
3. ถ้าจำเป็นต้องเปลี่ยนระบบ ให้เริ่มโดยมีหลักฐานและความเข้าใจ AI ขององค์กรติดมือไปด้วย

internal app จะกลายเป็นการศึกษาความต้องการที่ถูกที่สุดเท่าที่เคยมีมาสำหรับโปรเจกต์ใหญ่ และถ้า pilot พิสูจน์ว่าปัญหาคือกระบวนการ ไม่ใช่แพลตฟอร์ม — คุณอาจเพิ่งประหยัดโปรเจกต์หลายปีไปได้เลย
