ถ้าคุยกับผู้นำงาน innovation ในธนาคาร บริษัทประกัน เทเลคอม กลุ่มโรงพยาบาล หรือกลุ่มค้าปลีกไทย จะได้ยินเรื่องเดิมซ้ำ ๆ เกือบคำต่อคำ: *เราทำ AI proof of concept มาแล้ว มันเวิร์กดี แต่แล้วก็ไม่มีอะไรตามมา*

PoC เหล่านั้นไม่ได้ล้มเหลวเชิงเทคนิค เดโมออกมาดี โมเดลตอบคำถามตัวอย่างได้ แต่ทำไมจึงมีน้อยมากที่รอดไปถึง production? จากงานที่เราสร้างเครื่องมือ AI ภายในองค์กรให้บริษัทไทย เราพบสาเหตุเชิงโครงสร้างซ้ำ ๆ สามข้อ และไม่มีข้อไหนเกี่ยวกับคุณภาพโมเดลเลย

## เหตุผลที่ 1: PoC ถูกออกแบบมาเพื่อสร้างความประทับใจ ไม่ใช่เพื่อใช้งานจริง

PoC มักถูกสร้างมาเพื่อชนะการประชุม มันรันบนข้อมูลตัวอย่างที่คัดมาแล้ว มีคนเดียวที่ใช้ได้คล่อง และเส้นทางเดโมถูกซ้อมมาแล้ว พอต้องเจอข้อมูลจริงที่รก — ใบแจ้งหนี้สแกนที่ปนภาษาไทยกับอังกฤษ ข้อความลูกค้าที่ไม่ชัดเจน ไฟล์กระทบยอดที่รูปแบบวันที่ผิด — ช่องว่างระหว่าง "เดโม" กับ "ใช้งานจริง" ก็โผล่มาทันที

ไม่มีใครตั้งงบปิดช่องว่างนี้ เพราะ PoC ไม่เคยถูกกำหนดขอบเขตให้รวมมันไว้ โปรเจกต์จึงกลับไปอยู่ในสไลด์ที่มันมาจาก

## เหตุผลที่ 2: ไม่มีใครเป็นเจ้าของตัวเลข

ลองถามว่าใครรับผิดชอบผลลัพธ์ มักได้ยินความเงียบ ทีม innovation รัน PoC แต่เจ้าของ P&L — ฝ่าย operations การเงิน หรือบริการลูกค้า — ไม่เคยลงนามรับตัวชี้วัดไหนเลย เมื่อไม่มีตัวเลขที่เจ้าของธุรกิจสนใจ ก็ไม่มีวางจริงใจที่จะบอกว่า pilot สำเร็จหรือล้มเหลว และงบบรรทัดที่สองก็ไม่มีอะไรให้ยืน

## เหตุผลที่ 3: ขอบเขตไม่มีที่สิ้นสุด

"ทำ AI ให้ contact centre หน่อย" ไม่ใช่ขอบเขต แต่เป็นคำอธิษฐาน เมื่อขอบเขตงานไม่ชัด pilot ก็จบไม่ได้ และ pilot ที่จบไม่ได้ก็แยกยากจากความล้มเหลวที่ยังไม่ประกาศ งานที่มีขอบเขตจบได้ งานที่ไร้ขอบเขตจะละลายหายไป

## paid pilot ที่ดีควรพิสูจน์อะไร

Pilot ไม่ใช่เดโมที่ยาวขึ้น แต่เป็นสัญญาระยะสั้นกับความเป็นจริง เมื่อเรากำหนดขอบเขต pilot แบบจ่ายเงิน 4–8 สัปดาห์กับองค์กรไทย เรายืนยันคุณสมบัติสี่ข้อ:

| คุณสมบัติ | คำถามที่ตอบ | อาการเมื่อขาด |
|---|---|---|
| งานเดียว | งานไหนถูกทำให้ดีขึ้นอย่างวัดผลได้? | ขอบเขตบานปลายเป็น "แพลตฟอร์ม AI" |
| ตัวเลขฐาน | งานนี้ใช้เวลาหรือต้นทุนเท่าไรวันนี้? | ความสำเร็จกลายเป็นการเถียงกัน ไม่ใช่การวัด |
| ข้อมูลจริง ผู้ใช้จริง | ใครใช้งานทุกวันกับข้อมูลจริง? | เดโมเวิร์ก แต่ใช้งานจริงไม่เวิร์ก |
| เงื่อนไขการจบ | ผลแบบไหนทำให้ขยาย ปรับ หรือหยุด? | pilot ไม่เคยสรุป |

เงื่อนไขการจบสำคัญมาก การตกลง *ล่วงหน้า* ว่า "ถ้าเครื่องมือช่วยประหยัดไม่ถึง X ชั่วโมงต่อสัปดาห์ เราหยุด" เป็นการเจรจาที่ไม่สบายใจ — และนั่นแหละคือสิ่งที่ทำให้ pilot น่าเชื่อถือเวลาขึ้นที่ประชุมผู้บริหาร Pilot ที่ถูกอนุญาตให้จบ คือ pilot ที่ทุกคนเชื่อผลของมันได้

## ลำดับที่ใส่ในหนึ่งไตรมาสได้

```
สัปดาห์ 0     สัปดาห์ 1–3        สัปดาห์ 4–6        สัปดาห์ 7–8
┌─────────┐  ┌───────────┐    ┌────────────┐    ┌──────────┐
│ เลือกงาน │  │ สร้าง v1  │    │ ใช้จริงแบบ │    │ ตัดสินใจ │
│ + ตัวชี้วัด│→ │ กับข้อมูล │ →  │ คุมเข้ม +  │ →  │ ด้วยตัว  │
│         │  │ จริง      │    │ เก็บ log   │    │ เลขจริง  │
└─────────┘  └───────────┘    └────────────┘    └──────────┘
```

สังเกตว่ามีเวลาสร้างแค่สามสัปดาห์ ที่เหลือคือการใช้งานจริงและการตัดสินใจ — ส่วนที่ PoC มักข้าม และส่วนที่ผลิตหลักฐานที่ CFO ต้องการ

## ทำไมต้อง "จ่ายเงิน"

เรารับ pilot เฉพาะที่เป็นแบบจ่ายเงิน และแนะนำให้ระวัง vendor ที่ยื่นทำฟรี การจ่ายเงินเปลี่ยนพฤติกรรมทั้งสองฝ่าย: vendor ต้องกำหนดขอบเขตให้แน่น เพราะการทดลองฟรีไม่จำกัดคือขาดทุนที่รับไม่ได้ และผู้ซื้อจะจริงจัง เพราะเงินที่ลงไปคือความตั้งใจที่ลงไป pilot แบบจ่ายเงินที่มีเงื่อนไขจบ คือหน่วยที่เล็กที่สุดและตรงไปตรงมาที่สุดของ enterprise AI

## บริบทไทยช่วยให้เรื่องนี้ง่ายขึ้น ไม่ใช่ยากขึ้น

องค์กรไทยมีข้อได้เปรียบจริง: ช่องทางลูกค้าที่อยู่บน LINE อย่างเข้มข้น การตัดสินใจที่รวดเร็วเมื่อขอบเขตชัด และทีมที่มีความรู้กระบวนการลึกซึ่งเป็น ground truth ที่เครื่องมือ AI ต้องการ อุปสรรคทั้งสามข้อข้างบนเป็นเรื่องโครงสร้าง ไม่ใช่วัฒนธรรม — และแก้ได้ด้วยวิธีออกแบบ engagement แรก

เลือกงานเดียว วัดฐาน รันกับข้อมูลจริงและทีมที่เป็นเจ้าของงาน ตกลงความสำเร็จล่วงหน้า นั่นคือวินัยทั้งหมด — และคือความต่างระหว่าง PoC ถัดไป กับเครื่องมือ AI ตัวแรกที่ขึ้น production ได้จริง
